# CI/CD for NextJS Project

## Introduction

This article covers how i set up a CI/CD pipeline for auto-deployment on my personal web. I use NextJS 14 for the tech stack. I will use Docker to containerize the NextJS app and use NGINX as a web server and reverse proxy. for the runner, i use GitHub Actions.

## Docker

### What is Docker

> Docker is an open platform for developing, shipping, and running applications. Docker enables you to separate your applications from your infrastructure so you can deliver software quickly. With Docker, you can manage your infrastructure in the same ways you manage your applications. By taking advantage of Docker's methodologies for shipping, testing, and deploying code, you can significantly reduce the delay between writing code and running it in production.
>
> <br /> Source:
> [docs.docker.com](https://docs.docker.com/get-started/docker-overview/)

This article only covers how i containerize my app, if you want to know more or dive deep into how Docker works, or other features like persistent storage or networking inside it, you can explore the documentation.

I use a minimal Docker set up in this pipeline, i just need a dockerfile and docker compose. For the Dockerfile, i use two separate files for different environments (development and production). This separation makes it esier to manage. For example, if i want to make changes or experiment with the Docker config in the development environment without affecting the production environment. These files will also be used in separate GitHub Actions workflows, since i use two different workflow files for development and production.

Here are the dockerfiles:

`Dockerfile.dev` and `Dockerfile.dev`

```dockerfile

FROM node:22-alpine AS dependency

WORKDIR /app
COPY package.json .
COPY package-lock.json .
RUN npm install --legacy-peer-deps

FROM node:22-alpine AS builder
WORKDIR /app
COPY . .
COPY --from=dependency /app/node_modules ./node_modules
RUN npm install --cpu=x64 --os=linux --libc=glibc sharp
RUN npm run build

FROM gcr.io/distroless/nodejs22-debian12:latest-amd64 AS runner
WORKDIR /app
COPY --from=builder /app/public ./public
COPY --from=builder /app/.next/standalone ./
COPY --from=builder /app/.next/static ./.next/static
ENV NODE_ENV=production
CMD ["server.js"]
```

### Docker Compose

> Docker Compose is a tool for defining and running multi-container applications. It is the key to unlocking a streamlined and efficient development and deployment experience.
>
> <br /> Source: [docs.docker.com](https://docs.docker.com/compose/)

Docker Compose makes it easy to manage services, networks, and volumes with a single yaml file. It will be useful because i will use two services: one for production and one for development. Each services will also be used in different GitHub Actions workflows.

`docker-compose.yml`

```yaml
services:
  personal-web-dev:
    image: pawitrawarda/docker_shonen_dev:latest
    container_name: docker_shonen_dev_ctr
    ports:
      - "127.0.0.1:8093:3000"
    restart: unless-stopped
    mem_limit: 128m
    memswap_limit: 256m
  personal-web-prod:
    image: pawitrawarda/docker_shonen_prod:latest
    container_name: docker_shonen_prod_ctr
    ports:
      - "127.0.0.1:8092:3000"
    restart: unless-stopped
    mem_limit: 128m
    memswap_limit: 256m
```

## Server Configuration

### NGINX

> NGINX is a web server that can also be used as a reverse proxy, load balancer, mail proxy and HTTP cache.
>
> <br /> Source: [wikipedia](https://en.wikipedia.org/wiki/Nginx)

I will use NGINX as reverse proxy inside my VPS, so the browser not directly access the container.

I use this configuration:

`nginx-conf.d`

```nginx
server {
    listen 443 ssl http2;
    listen [::]:443 ssl http2;
    ssl_certificate         /<path>/<your_certificate_file>.pem; #path to your public key
    ssl_certificate_key     /<path>/<your_certificate_file>.key; #path to your private key

    server_name shonen-dev.xyz; # the hostname
    location / {
        proxy_pass http://127.0.0.1:8092;

        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

    }
}

```

As seen above, `proxy_pass` point to the container inside the VPS that runs on 127.0.0.1:8092, and there is some additional `proxy_set_header` config.

- `Host $host;`

  Forwards the domain name that client requested (shonen-dev.xyz) to the containerized application so the application doesn't think the request came from 127.0.0.1.

- `X-real-IP $remote_addr;`

  Sends the client's original IP address to the containerized application. Without this, the application will only see Nginx IP (127.0.0.1).

- `X-Forwarded-For $proxy_add_x_forwarded_for;`

  Records the IP chain if there is more than one proxy (Cloudflare -> Nginx -> Container App).

- `X-Forwarded-Proto $scheme;`

  Tells the application that client is already using HTTPS protocol (Browser -> Nginx), even though communication between Nginx and the containerized application uses HTTP (Nginx -> Container App). This is important for security, auth, and URL redirects, especially if you are using cookie.

## Github Action

> GitHub Actions is a continuous integration and continuous delivery (CI/CD) platform that allows you to automate your build, test, and deployment pipeline. You can create workflows that build and test every pull request to your repository, or deploy merged pull requests to production.
>
> <br /> Source:
> [docs.github.com](https://docs.github.com/en/actions/get-started/quickstart)

To create workflows, you can just define a YAML file under the `.github/workflows` folder. As i mentioned before, i will use 2 workflow for production and development, and one more workflow to run the linter.

the complete folder structure will look like this:

```text
project-root/
├── .github/
│   └── workflows/
│       ├── lint.yml
│       ├── build-and-deploy-dev.yml
│       └── build-and-deploy-prod.yml
│
├── src/
├── public/
├── Dockerfile.dev
├── Dockerfile.prod
├── docker-compose.yml
└── package.json
```

### Set Repository Secrets

To connect the GitHub Actions workflows and the server, i use `appleboy/ssh-action@master`, so i need to define some repository secrets in the GitHub repo. In the repository, go to menu **Settings -> Secrets and Variables -> Actions**. Click the **New repository secret** button and add these variables to the Repository Secrets:

- `host`

  Server IP.

- `username`

  Server username.

- `key`

  Your generated SSH private key. You can generate a private key using this command on your server:

  ```bash
  ssh-keygen -t ed25519 -C "your_email@example.com"
  ```

- `port`

  SSH server port (22).

- `passphrase`

  Your passphrase when generating SSH key. You can omit this if you didn't define a passphrase.

Those secrets will be used in the GitHub Actions workflows.

The workflow looks like this:

`lint.yml`

```yaml
name: Lint
on:
  pull_request:
    branches:
      - main
      - development

env:
  NODE_VERSION: 18

jobs:
  linting:
    name: Linting
    runs-on: ubuntu-latest
    steps:
      - name: Code Checkout
        uses: actions/checkout@v4

      - name: Install Bun
        uses: oven-sh/setup-bun@v2
        with:
          bun-version: latest

      - name: Install Dependencies
        run: bun install

      - name: Code Linting
        run: bun --bun run lint
```

To prevent merging if there is an error in the linter, i need to set up a branch protection rule in the GitHub. Go to **Settings -> Branchs -> Add rule**. Check **Require status checks to pass before merging** and add your linter workflow.

### Deployment Workflow

As i mentioned before, i use two different workflows (development and production). For the development branch, the trigger will start when ther is a merge on development branch, and for production on the main branch.
So i will only put one example of the YAML file here, The differences are only in the IMAGE_NAME, the target branch, and the Docker Compose service name.

`build-and-deploy.yml`

```yaml
name: Build and Deploy Web shonen-dev to Development

on:
  push:
    branches: [development]

  workflow_dispatch:
    inputs:
      version:
        description: "Development"
        required: true
        type: string

#2
env:
  IMAGE_NAME: "docker_shonen_dev"

#3
jobs:
  build_and_push:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout the repo
        uses: actions/checkout@v2

      - name: Log in to Docker Hub
        uses: docker/login-action@f054a8b539a109f9f41c372932f1ae047eff08c9
        with:
          username: ${{ secrets.DOCKER_USERNAME }}
          password: ${{ secrets.DOCKER_PASSWORD }}

      - name: Extract metadata (tags, labels) for Docker
        id: meta
        uses: docker/metadata-action@98669ae865ea3cffbcbaa878cf57c20bbf1c6c38
        with:
          images: pawitrawarda/${{ env.IMAGE_NAME }}

      - name: Build and push Docker image
        uses: docker/build-push-action@ad44023a93711e3deb337508980b4b5e9bcdc5dc
        with:
          context: .
          file: ./Dockerfile.dev
          push: true
          tags: pawitrawarda/${{ env.IMAGE_NAME }}:latest
          labels: latest

  deploy:
    runs-on: ubuntu-latest
    needs: build_and_push
    steps:
      - name: Checkout the repo
        uses: actions/checkout@v4

      - name: Create directory on server
        uses: appleboy/ssh-action@master
        with:
          host: ${{ secrets.HOST_KAZUHA }}
          username: ${{ secrets.USERNAME }}
          key: ${{ secrets.SSHKEY_KAZUHA }}
          port: ${{ secrets.PORT }}
          passphrase: ${{ secrets.PASSPHRASE_KAZUHA }}
          script: |
            # Create directory if doesn't exist
            sudo mkdir -p /opt/apps-container/personal-web

      - name: Copy docker-compose.yml to server
        uses: appleboy/scp-action@v1
        with:
          host: ${{ secrets.HOST_KAZUHA }}
          username: ${{ secrets.USERNAME }}
          key: ${{ secrets.SSHKEY_KAZUHA }}
          port: ${{ secrets.PORT }}
          passphrase: ${{ secrets.PASSPHRASE_KAZUHA }}
          source: "./docker-compose.yml"
          target: "/opt/apps-container/personal-web/"

      - name: Deploy using Docker Compose
        uses: appleboy/ssh-action@master
        with:
          host: ${{ secrets.HOST_KAZUHA }}
          username: ${{ secrets.USERNAME }}
          key: ${{ secrets.SSHKEY_KAZUHA }}
          port: ${{ secrets.PORT }}
          passphrase: ${{ secrets.PASSPHRASE_KAZUHA }}
          script: |
            # Navigate to the directory and deploy
            cd /opt/apps-container/personal-web

            # Pull latest image
            docker compose pull personal-web-dev

            # Stop and remove existing container
            docker compose down --remove-orphans personal-web-dev

            # Start services
            docker compose up -d --force-recreate personal-web-dev

            # Check status of the containers
            docker compose ps

            # Remove unused images
            docker image prune -f
```

To make sure GitHub Actions is works, you can try making a pull request to the development branch. After it is merged into development branch, go to the **Actions** tab, and you will see a list of all the workflows and can monitor them.
