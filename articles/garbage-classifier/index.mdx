# Building a Zero-Shot Garbage Classifier API with FastAPI and OpenAI CLIP

## Introduction

Recently, I decided to build a fun side project using **OpenCode Go**: a **Garbage Classifier API**. The idea was simple—I wanted to build an API where you can upload an image of a piece of trash, and the system automatically identifies what kind of waste it is along with its confidence score.

Instead of training a custom computer vision model from scratch with thousands of garbage images, I used a **Zero-Shot Image Classification** approach powered by OpenAI's **CLIP (Contrastive Language-Image Pre-training)** model from Hugging Face. With zero-shot classification, the model can classify images into text categories it was never explicitly fine-tuned on!

You can try the live demo directly via the Swagger UI here: [api.shonen-dev.xyz/api/docs](https://api.shonen-dev.xyz/api/docs) or check out the complete source code on my GitHub repository: [shonenxnaifu/garbage-classifier](https://github.com/shonenxnaifu/garbage-classifier).

![Garbage Classifier API Swagger UI](https://res.cloudinary.com/dbegkzvdt/image/upload/v1795076120/Screenshot_2026-11-19_at_3.15.07_PM_vwrpo9.png)

## Tech Stack & Dependencies

To keep the API fast and easy to containerize, I built it with Python and ran the CPU version of PyTorch so it can run on a standard server without requiring a dedicated GPU:

- **FastAPI** - Modern Python web framework for handling HTTP requests and generating Swagger UI (`/api/docs`)
- **Transformers (Hugging Face)** - For loading and running the `openai/clip-vit-base-patch32` model
- **PyTorch (`torch==2.3.0+cpu`)** - Deep learning framework for tensor calculations and model inference
- **Pillow (`PIL`)** - For reading and preprocessing uploaded image bytes
- **Pydantic** - For validating and structuring the classification JSON response
- **Uvicorn** - ASGI server for running the FastAPI application
- **Docker** - For containerizing the application and its ML dependencies

## How It Works & Waste Categories

The architecture of this project is straightforward:

1. A user uploads an image file via a `POST` request to the FastAPI endpoint.
2. **Pillow** processes the image bytes and converts them into an RGB image.
3. The **CLIPProcessor** encodes both the uploaded image and the list of candidate waste labels into tensors.
4. The **CLIPModel** calculates the similarity logits between the image and each text label, applies a `softmax` function to get probability scores, and returns the top matching category.

### Defining the Waste Labels

Initially, I tested the API with 8 basic categories (`plastic bottle`, `glass bottle`, `paper`, `cardboard`, `metal can`, `organic waste`, `electronic waste`, and `textile`).

Later, I expanded the classification scope in `WASTE_DEFINITION.md` by breaking down waste into **5 primary categories** with over **80 specific candidate labels**:

- **Organic Waste**: _food scraps, vegetable waste, fruit peels, coffee grounds, fallen leaves, egg shells, etc._
- **Hazardous Waste**: _batteries, lithium batteries, paint cans, medical waste, used syringes, expired medicines, electronic waste, etc._
- **Solid Waste**: _plastic packaging, food containers, disposable utensils, discarded clothing, broken furniture, construction debris, etc._
- **Liquid Waste**: _used cooking oil, motor oil, chemical wastewater, detergent wastewater, etc._
- **Recyclable Waste**: _PET containers, HDPE containers, cardboard boxes, aluminum cans, glass jars, scrap metal, etc._

### 1. Zero-Shot Image Classification

Because it uses `openai/clip-vit-base-patch32`, adding or changing waste categories does not require retraining the model. I only need to update the array of text labels in the code, and CLIP will immediately evaluate images against the new labels.

### 2. Detailed Confidence Scores

### 3. Startup Model Pre-loading & CPU Optimization

The CLIP model is loaded once at application startup in `app/clip_model.py` rather than on every request, keeping inference responsive. In addition, using the CPU-only PyTorch wheel (`torch==2.3.0+cpu`) significantly reduces the Docker image size compared to bundling full CUDA libraries.

### 4. Docker Memory Analysis (Alpine vs. Debian-Slim)

While containerizing this project, I also tested whether using an `alpine` base image would save runtime RAM compared to `python:3.10-slim`. The benchmark showed only a ~1 MB difference at runtime—negligible compared to the CLIP model itself (~500–800 MB in memory)—while `slim` offers much better compatibility with PyTorch wheels (`manylinux`).

## Conclusion

Experimenting with **OpenCode Go** to build this **Garbage Classifier API** was a great way to explore practical AI integration. By combining Hugging Face's **CLIP** model with **FastAPI**, it is surprisingly easy to build a flexible, zero-shot image classification service without the overhead of collecting datasets or training a model from scratch.
